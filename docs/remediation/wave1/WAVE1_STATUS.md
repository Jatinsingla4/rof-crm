## Findings that explain why earlier fixes did not hold
1. The three financial flags (`agreement_snapshot_v1`, `receipt_allocation_v1`, `commission_requires_cleared_v1`) default to `off` in code. `commission_requires_cleared_v1` has no seed row at all. The fixes only exist when finance sets them on. Production values are unknown from here (needs a read-only DB check).
2. Nothing in the UI reads the agreement snapshot. Pricing card, Applicant File, ledger reports, Demand Status and the quote all recompute from the CURRENT unit master or from separate formulas (12 disagreement points were listed by the code map, summarised below).
3. `receipts.status` and `approval_status` were unlinked. The clear route checked `authorized_by` only. About 60 inline `status = 'cleared'` readers exist besides the central helper.

## Known gaps in what was done
- Pricing: the plan total is treated as the sold price. If a plan was ever cut wrongly, the reports now show that wrong price instead of the unit master one; the existing `scheduleGap` / `/booking/agreement-shadow` checks remain the way to find such bookings. The Applicant File now subtracts the approved rebate from Net Basic Price when a plan exists (before, it did not), which is the plan's own definition but is a visible change finance should confirm. The Applicant File page change was type-checked and its numbers are covered through the shared formula, but the 77 older `docs/*` scripts (some read the Applicant File and reports) were not run here.
- Reader side not swept. About 60 inline `status = 'cleared'` predicates (reports, dashboard, demands, payments) and `eligibleReceipt()` still do not look at `approval_status`. The 12 historical cleared-but-unapproved receipts (Rs 30,54,936 per the brief) therefore still count as money everywhere, consistently. Excluding them needs the sweep plus an ROF decision on their treatment.
- Bounce route needs only the payments right, not the receipt checker right. Commission payout has no checker step. Both are policy questions (decision below).
- The migration trigger was only run on a fresh throwaway database, not on a copy of production data.
